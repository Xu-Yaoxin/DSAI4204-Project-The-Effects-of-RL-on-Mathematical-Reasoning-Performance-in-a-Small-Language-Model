# MATH Level 4：两台机器完成 RL 测评

推荐从旧机直接部署新机，完整命令见 `DIRECT_TRANSFER.md`。本地只同步小型分批代码到旧机，模型和固定实验文件由两台新机直接拉取；旧机 Base 保持运行。

当前部署使用三台机器：旧机器只完成正在运行的 Base；另外两台新机器分别运行 RL。

本包把已选定的 `checkpoint-384` 的正式 RL 测试分为两个独立任务。每台机器运行一个串行进程，每批 100 道题、每题 16 次回答，共 1,600 次。两批合并后仍是原定的 200 道题、3,200 次回答。

| 批次 | 命令参数 | 原测试集中的题目序号（从 1 开始） | 输出目录 |
|---|---|---|---|
| 第一批 | `--shard-index 0` | 1、3、5……199 | `rl_shards/shard_0` |
| 第二批 | `--shard-index 1` | 2、4、6……200 | `rl_shards/shard_1` |

输出目录均位于 `math_l4_v1/outputs/math_l4_v1_fix1/`。具体题目 ID 和学科数量见 `plans/batch_0.json`、`plans/batch_1.json`。

## 使用顺序

完整命令见 [COMMANDS.md](COMMANDS.md)：

1. 用 `upload_base_stop.sh` 给旧机上传控制器，启动 `watch_base_only.py`。当前 Base 继续运行，完整结束后停止原流水线，不启动 RL。
2. 在 Mac 运行 `download_current.sh`，增量下载模型、数据和当前结果，并准备上传文件。
3. 分别用 `upload_batch.sh 0 ...` 和 `upload_batch.sh 1 ...` 上传到两台额外的新机器。
4. 两台新机器使用 `setup_worker.sh` 安装锁定依赖，再分别执行第 0、1 批；均可立即开始。
5. 分别回收旧机 Base、新机第 0 批及第 1 批，严格合并后进行配对分析。

下载文件夹默认是 `~/Downloads/math_l4_selected_20261104`。再次下载会更新其中的回答和日志；尚在运行的文件属于各自复制时刻的快照，不是原子快照。只有完整 JSONL 行可计为已生成回答，最终 Base 分析还要求完整 manifest 和样本哈希通过检查。

## 模型和选点证据

实际推理模型是完整 `Qwen/Qwen3.5-2B-Base` 加 `checkpoint-384` 的 LoRA adapter。不会在迁移过程中重新训练或合并权重。

选点记录是用户已确认的：128 步 255/512、256 步 299/512、384 步 309/512。代码仍要求完整验证三个候选的来源，所以下载脚本保留 128、256、384 的检查点；上传包只带它们的 adapter 配置、参数和封存记录，以及三组验证回答、正式训练报告所绑定的证据。较早候选不会用于本次测试推理。

上传包包含原始冻结代码、完整数据、依赖安装脚本和锁文件，但不包含正在增长的 `test_base/`、`test_rl/`、`run_state.json` 或实验日志。这样上传到旧机器时不会把实时状态覆盖成旧快照。Base 的参考 manifest 单独存为 `reference/base_manifest.json`。

## 可比性和执行约束

两个任务要求单张 RTX 4090、Linux x86_64、CPython 3.11，以及与 Base 一致的锁定软件版本。每个进程使用 4 个计算线程、1 个 interop 线程；同一张 GPU 不同时跑 Base 和 RL，也不同时跑两批。新机器如果使用 A100 或其他 GPU，本版本会明确拒绝启动，因为五分钟墙钟限制会让硬件性能直接影响回答预算。

每道题的 prompt、种子、temperature、top-p、BF16、SDPA、EOS、原生上下文上限、300 秒超时及重复检测均使用原实现。没有安装新的快速算子。CPU 型号、驱动、可用内存等仍可能因机器不同而变化，硬件审计会记录这些差异；匹配 GPU/软件不等于证明吞吐量完全相同。

`evaluate_shard.py` 对原 `evaluate.py` 的精确 SHA-256 做检查，在内存中只扩展两处调度逻辑，并注入执行来源记录。原文件不改写。分片 manifest 保存 wrapper 哈希、实际编译源码哈希、分配规则和题目集合哈希。生成、评分、种子与 guard 的代码沿用原字节。

本版本保留当前评分协议以便与已运行的 Base 配对。此前发现的验证集标签和答案抽取问题没有被迁移过程悄悄修正；后续质量分析应统一重放评分，并明确区分原始选点、修正后的诊断以及最终结论。

## 续跑和日志

再次执行同一批命令会验证并跳过已完整保存的回答。续跑以完整回答为单位，中断时尚未保存的一条会重新生成，不恢复中间 token。明确持久化了一条 guard 结果、以 75 退出的进程，最多自动恢复两次；其他异常会退出并保留证据。损坏的最后一行不会被自动删除。新进程持有原项目的单 GPU 锁，防止误启动另一套完整流程。

控制器启动时先输出 `[PIDFD READY]`：它只对自身执行 signal 0 能力检查，不暂停 Base。若 Linux x86_64 上的 Python 没有暴露 pidfd 接口，`pidfd_compat.py` 会直接调用同一内核接口；仍保留 pidfd、进程启动时间和命令校验。内核不支持或容器拒绝调用时会明确退出，不退回按 PID 盲目终止进程。出现启动报错表示“Base 完成后自动停止”尚未生效，不能只凭后台 PID 判定控制器正常。

`watch_base_only.py` 先精确停用同一实验的旧切换监控器，再运行 `switch_after_base.py --stop-only`。它不重启当前 Base；Base 完整保存并通过校验后才停止原流程，释放锁，并写入 `outputs/base_stop_receipt.json`。日志 `[STOPPED AFTER BASE]` 表示完成，不会接着启动 RL。原 runner 状态可能显示 `interrupted`，这是有意停止后续阶段。

如果旧流程抢先开始了少量 RL 回答，这些回答仍保留在原 `test_rl/`，不会自动混入新分片。若独立 RL shard 已经在旧机运行，控制器会报错并保留该任务。两台新机器都无需等待 Base，各自完成固定 100 题的一批。

## 合并和检查范围

`merge_shards.py` 要求两个分片分别完成全部 1,600 次回答，验证题目、种子、模型、adapter、选点、软件、GPU 和停止策略，并拒绝重复、遗漏或修改。合并结果保留两个来源的哈希与调度扩展信息，最后再经过原完整评测验证器。

本地检查包括实际冻结数据的分配计划，以及不加载模型的合并、续跑、进程切换和上传过滤 fixtures。真实 Linux CUDA 安装与两机推理需要在目标服务器上执行；本地 CPU 检查不代表已经完成 GPU 验证。验证记录见 `validation/`。
